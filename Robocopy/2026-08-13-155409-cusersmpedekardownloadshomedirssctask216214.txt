  Why it's almost certainly ADS

  Look at what your tests eliminated and what they left standing:

  Something is attached to these specific files that (a) survives rename and
  extension change, (b) survives a copy to NTFS, and (c) is rejected only by the
  Pure destination. That is the signature of an NTFS Alternate Data Stream.

  The corroborating evidence is in the file list itself: almost every failure is
  an internet-sourced image or joke file — \home\kr\Personal\ is full of
  .jpg/.gif/.bmp downloads, plus .htm and .cmd. Files like these carry a
  Zone.Identifier stream (Mark-of-the-Web) that Windows stamps on anything
  downloaded from a browser or email. Robocopy copies alternate data streams by
  default (there is no switch to disable it), and Explorer does too — so when
  the write reaches the Pure Storage FlashBlade SMB share, which does not 
  implement NTFS named streams, the stream write fails with:

  - Win32 ERROR 123 / 0x7B (ERROR_INVALID_NAME) → what Robocopy reports
  - "The file name you specified is not valid or too long" → the exact Explorer
  wording for a rejected stream name

  The filename:streamname:$DATA syntax is what's "invalid" to the target — not
  your file's name.

  Confirm it in 10 seconds

  Run this against any one failing file (PowerShell):

  Get-Item -LiteralPath 'D:\Homedirs\dt72023\home\kr\Personal\ass.jpg' -Stream *

  Or the classic:

  dir /r "D:\Homedirs\dt72023\home\kr\Personal"

  If you see a second stream (e.g. :Zone.Identifier:$DATA, or something like
  :AFP_AfpInfo, :com.apple..., a scanner/AV stream, etc.) alongside :$DATA, that
  is the culprit. A clean file will show only :$DATA.

  How to fix the migration

  The goal is to strip the extra stream(s) — the primary file data is untouched.
  Options, in order of preference:

  1. If it's only Zone.Identifier (most likely): unblock in place, then re-run
  Robocopy.
  Get-ChildItem -LiteralPath 'D:\Homedirs' -Recurse -File | Unblock-File
  1. Unblock-File removes only the Zone.Identifier stream and nothing else —
  safe and reversible in effect.
  2. If there are other/unknown streams, remove every non-primary stream
  explicitly:
  Get-ChildItem -LiteralPath 'D:\Homedirs' -Recurse -File |
    ForEach-Object {
        Get-Item -LiteralPath $_.FullName -Stream * |
          Where-Object Stream -ne ':$DATA' |
          ForEach-Object { Remove-Item -LiteralPath $_.FileName -Stream
  $_.Stream }
    }

  Either way, the corrected copy operation itself is unchanged — the streams
  simply no longer exist to be rejected.

  ⚠️ Before you strip anything on the source, confirm with the data owner that
  no stream is meaningful (rare, but scanner/DMS products occasionally store
  metadata in ADS). The safest pattern is: copy to an NTFS staging area first,
  strip there, then Robocopy the staged copy to Pure — leaving the original file
  server pristine until the migration is signed off.
