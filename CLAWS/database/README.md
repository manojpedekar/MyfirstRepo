# Database Migration Scripts

This directory contains SQL scripts for migrating NTFS permission data from SQLite databases (generated by CollectNTFSPerms) to enterprise-class database management systems.

## Directory Structure

```
database/
├── MSSQL/          # Microsoft SQL Server scripts
├── PostgreSQL/     # PostgreSQL scripts
├── Oracle/         # Oracle Database scripts
└── MySQL/          # MySQL scripts
```

Each subdirectory contains five numbered SQL scripts that must be executed in order:

1. **001_create_schemas.sql** - Creates database schemas (or equivalent structures)
2. **002_create_tables.sql** - Creates all application and lookup tables
3. **003_create_indexes.sql** - Creates indexes for query performance
4. **004_seed_lookups.sql** - Populates lookup/reference tables with initial data
5. **005_create_views.sql** - Creates database views for common query patterns

## Schema Version

All scripts maintain **schema version 1.5.0**, matching the original SQLite schema from CollectNTFSPerms.

## Script Execution Order

**IMPORTANT:** Scripts must be executed in numerical order (001 → 002 → 003 → 004 → 005).

The MigrateNTFSPerms tool automatically executes scripts in the correct order when using the `--createdbonly` option.

## Developer Note

The file `MSSQL/000_Create_local_testing_db_with_Drop.sql` is for local development only and **must not** be executed by MigrateNTFSPerms. It contains destructive operations (DROP DATABASE) for testing purposes.

## Platform-Specific Differences

### Microsoft SQL Server (MSSQL)

**Connection:** Default port 1433

**Schema Support:** Native schema support with `[schema].[table]` syntax
- `[fsapp].[TableName]` - Application data tables
- `[fslkp].[TableName]` - Lookup/reference tables
- `[fssimport].[TableName]` - Data import staging tables

**Key Characteristics:**
- Uses `GO` batch separators
- Uses `IDENTITY(1,1)` for auto-increment columns
- Supports `UNIQUEIDENTIFIER` data type for GUIDs
- Uses `NVARCHAR` for Unicode strings
- Uses `BIT` for boolean values
- Uses `STRING_AGG` for string aggregation in views
- Uses `MERGE` statements for upserts
- Computed columns: `PathHash AS CONVERT(binary(32), HASHBYTES('SHA2_256', Path))`

**Special Syntax:**
```sql
CREATE TABLE [fsapp].[TableName] (
    ID INT IDENTITY(1,1) NOT NULL,
    Name NVARCHAR(256) NOT NULL,
    IsActive BIT NOT NULL
);
```

---

### PostgreSQL

**Connection:** Default port 5432

**Schema Support:** Native schema support with `schema.table` syntax
- `fsapp.tablename` - Application data tables
- `fslkp.tablename` - Lookup/reference tables
- `fssimport.tablename` - Data import staging tables

**Key Data Type Mappings:**
- `NVARCHAR` → `VARCHAR` or `TEXT`
- `BIT` → `BOOLEAN`
- `IDENTITY(1,1)` → `SERIAL` or `BIGSERIAL`
- `DATETIME2`, `datetimeoffset` → `TIMESTAMP WITH TIME ZONE`
- `VARBINARY` → `BYTEA`
- `UNIQUEIDENTIFIER` → `UUID`

**Key Differences:**
- No `GO` batch separators
- Uses `CREATE SCHEMA IF NOT EXISTS`
- Uses `CREATE TABLE IF NOT EXISTS`
- Uses `INSERT ... ON CONFLICT DO UPDATE` instead of `MERGE`
- Computed columns: `PathHash bytea GENERATED ALWAYS AS (digest(Path, 'sha256')) STORED`
- String aggregation: `STRING_AGG(column, ',' ORDER BY column)`
- Uses `RAISE NOTICE` for console output

**Special Syntax:**
```sql
CREATE TABLE IF NOT EXISTS fsapp.tablename (
    id SERIAL PRIMARY KEY,
    name VARCHAR(256) NOT NULL,
    is_active BOOLEAN NOT NULL
);
```

---

### Oracle Database

**Connection:** Default port 1521

**Schema Support:** User-based schemas (schemas are tied to database users)
- `fsapp.tablename` - Application data tables (owned by 'fsapp' user)
- `fslkp.tablename` - Lookup/reference tables (owned by 'fslkp' user)
- `fssimport.tablename` - Data import staging tables (owned by 'fssimport' user)

**Key Data Type Mappings:**
- `NVARCHAR(n)` → `NVARCHAR2(n)`
- `VARCHAR(n)` → `VARCHAR2(n)`
- `NVARCHAR(MAX)` → `CLOB`
- `BIT` → `NUMBER(1,0)` (0 = false, 1 = true)
- `INT` → `NUMBER(10,0)`
- `BIGINT` → `NUMBER(19,0)`
- `IDENTITY(1,1)` → `GENERATED ALWAYS AS IDENTITY`
- `DATETIME2`, `datetimeoffset` → `TIMESTAMP WITH TIME ZONE`
- `VARBINARY` → `RAW` or `BLOB`
- `UNIQUEIDENTIFIER` → `RAW(16)`
- `FLOAT` → `BINARY_DOUBLE`

**Key Differences:**
- Uses PL/SQL blocks for conditional logic (IF NOT EXISTS)
- Schema creation creates database users with passwords
- Uses `DBMS_OUTPUT.PUT_LINE` for console output (requires `SET SERVEROUTPUT ON`)
- Computed columns: `PathHash RAW(32) GENERATED ALWAYS AS (STANDARD_HASH(Path, 'SHA256')) VIRTUAL`
- String aggregation: `LISTAGG(column, ',') WITHIN GROUP (ORDER BY column)`
- Uses `BITAND()` function for bitwise operations
- Reserved keyword `GROUP` must be quoted as `"GROUP"`

**Special Syntax:**
```sql
BEGIN
    EXECUTE IMMEDIATE 'CREATE TABLE fsapp.tablename (
        id NUMBER(10,0) GENERATED ALWAYS AS IDENTITY,
        name NVARCHAR2(256) NOT NULL,
        is_active NUMBER(1,0) NOT NULL
    )';
EXCEPTION
    WHEN OTHERS THEN
        IF SQLCODE != -955 THEN RAISE; END IF;
END;
/
```

---

### MySQL

**Connection:** Default port 3306

**Schema Support:** Databases act as schemas; uses table name prefixes
- `fsapp_TableName` - Application data tables
- `fslkp_TableName` - Lookup/reference tables
- `fssimport_TableName` - Data import staging tables

**Key Data Type Mappings:**
- `NVARCHAR(n)` → `VARCHAR(n) CHARACTER SET utf8mb4`
- `BIT` → `TINYINT(1)` or `BOOLEAN`
- `IDENTITY(1,1)` → `AUTO_INCREMENT`
- `UNIQUEIDENTIFIER` → `BINARY(16)` or `CHAR(36)`
- `DATETIME2`, `datetimeoffset` → `DATETIME` or `TIMESTAMP`
- `VARBINARY` → `VARBINARY`

**Key Differences:**
- Uses database name instead of schema names
- Table names use prefixes: `fsapp_` for application tables, `fslkp_` for lookup tables, `fssimport_` for staging tables
- Uses `CREATE DATABASE IF NOT EXISTS` for schema creation
- Uses `INSERT ... ON DUPLICATE KEY UPDATE` instead of `MERGE`
- All tables use `ENGINE=InnoDB` for foreign key support
- Uses `CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci` for Unicode support
- Computed columns: `PathHash VARBINARY(32) AS (UNHEX(SHA2(Path, 256))) STORED`
- String aggregation: `GROUP_CONCAT(column ORDER BY column SEPARATOR ',')`
- Reserved keyword `Group` must be quoted as `` `Group` ``
- Uses `SELECT ... AS message` for console output

**Special Syntax:**
```sql
CREATE TABLE IF NOT EXISTS fsapp_TableName (
    ID INT AUTO_INCREMENT PRIMARY KEY,
    Name VARCHAR(256) CHARACTER SET utf8mb4 NOT NULL,
    IsActive TINYINT(1) NOT NULL
) ENGINE=InnoDB CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

## Common Schema Elements

All platforms implement the same logical schema with three primary groups:

### Application Data Tables (fsapp schema)

- **Version** - Schema version tracking
- **CollectionInfo** - Metadata about each NTFS scan/collection
- **SIDs** - Security identifiers and resolved account names
- **Disks** - Physical disk information
- **Volumes** - Logical volume information
- **VolumeMounts** - Volume mount point mappings
- **VolumeExtents** - Physical disk extent allocations
- **Partitions** - Disk partition information
- **Folders** - Directory/folder hierarchy with attributes
- **ACL** - Access Control List metadata
- **ACE** - Access Control Entries (individual permissions)
- **SMBShares** - SMB file share information
- **SMBShareAccess** - SMB share permission entries
- **EventLog** - Application event logging

### Lookup/Reference Tables (fslkp schema)

- **PropagationFlags** - ACE propagation flag enumeration
- **InheritanceFlags** - ACE inheritance flag enumeration
- **FileSystemRights** - File system permission mask enumeration
- **AceTypes** - ACE type enumeration
- **DriveTypes** - Windows drive type enumeration
- **MBR_Type** - MBR partition type codes
- **ShareAvailabilityTypes** - SMB share availability types
- **ShareCachingModes** - SMB share caching mode enumeration
- **ShareFolderEnumerationModes** - SMB folder enumeration modes
- **ShareLeasingModes** - SMB share leasing mode enumeration

### Data Import Staging Tables (fssimport schema)

- **Staging tables** - Temporary tables for importing data from external sources (e.g., CSV files, other databases)
- Used by data migration and integration processes
- Typically truncated or dropped after successful import

## Important Constraints

All platforms preserve the following:

### Primary Keys
- Every table has a primary key (composite keys for multi-tenant tables)

### Foreign Keys
- Referential integrity enforced between related tables
- Cascade delete rules on appropriate relationships

### Check Constraints
- Data validation at the database level
- Ensures data consistency (e.g., port numbers, sizes, date ranges)

### Unique Constraints
- Prevents duplicate data (e.g., unique SID per inventory)

---

## Indexes

Each platform implements the same logical indexes:

- **Unique indexes** on natural keys (e.g., InventoryID + SID)
- **Foreign key indexes** for join performance
- **Search indexes** on frequently queried columns (e.g., AccountName, Path)
- **Covering indexes** with INCLUDE columns (where supported)

---

## Views

All platforms implement 11 common views:

1. **vw_ACL** - ACL information with resolved folder paths and account names
2. **vw_ACE** - ACE permissions with resolved identities and inheritance
3. **vw_ACE_Decoded** - Detailed ACE information with decoded permissions
4. **vw_Folders** - Folder hierarchy with volume information
5. **vw_Volumes** - Volume information with mount points
6. **vw_PermissionSummary** - Summary of permissions by folder and identity
7. **vw_SIDResolution** - SID resolution status and details
8. **vw_FolderHierarchy** - Recursive folder hierarchy (where supported)
9. **vw_InheritanceChain** - Permission inheritance chains
10. **vw_SMBSharePermissions** - SMB share permissions with resolved trustees
11. **vw_DiskVolumeMapping** - Disk and volume relationship mapping

## Testing Scripts

When testing or developing database schema changes:

1. **NEVER** run `000_Create_local_testing_db_with_Drop.sql` in production
2. Always test schema creation on a separate test database first
3. Use transactions where supported to enable rollback on errors
4. Verify foreign key constraints are working correctly
5. Test views return expected results after schema creation

## Performance Considerations

### Indexes
- All platforms have equivalent indexes for consistent query performance
- Index strategies may differ due to platform-specific optimizers

### Partitioning
- For very large datasets (millions of folders), consider:
  - **MSSQL:** Table partitioning by InventoryID
  - **PostgreSQL:** Declarative partitioning by InventoryID
  - **Oracle:** Partition by hash on InventoryID
  - **MySQL:** Partition by hash on InventoryID

### Large Object Storage
- Path columns use appropriate large text types
- Consider separate tablespace for large text/binary columns in production
